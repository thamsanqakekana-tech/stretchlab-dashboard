## For Claude Code to action against the existing scripts

These are confirmed problems found by cross-referencing `analytics.py`, `benchmarks.py`, `validate_attribution.py`, and the JSON outputs. Each fix is described with the file, the problem, and the correct behaviour.

## Fix 1 — `analytics.py`: Show Rate Denominator

**File:** `analytics.py` → `calculate_revenue_intelligence()`

**Problem:** `show_rate` is calculated as `total_shows / total_bookings`. The `total_bookings` figure includes future/scheduled appointments that have no outcome yet. This always understates show rate and produces misleading numbers that look like a show rate crisis when the reality is timing.

**Required fix:** Show rate must use resolved bookings only.

```python
# WRONG — current behaviour
show_rate = (total_shows / total_bookings) if total_bookings > 0 else 0

# CORRECT — filter to past appointments only
resolved_bookings = bookings[bookings['is_past'] == 1]
resolved_count = len(resolved_bookings)
show_rate = (total_shows / resolved_count) if resolved_count > 0 else 0
```

Apply the same fix to `score_campaign_health()` which calls `calculate_revenue_intelligence()` and uses the returned `show_rate` to assess against the benchmark.

## Fix 2 — `analytics.py`: Campaign Health Score Uses Placeholder Values

**File:** `analytics.py` → `score_campaign_health()`

**Problem:** The engagement score (max 25) and goal alignment score (max 25) are hardcoded placeholders:
```python
engagement_score = 12  # Moderate engagement assumed
goal_score = 10  # Poor alignment assumed
```

A score with hardcoded sub-components is not a real score — it will never change regardless of what the data says, and will produce the same overall health level across all runs.

**Required fix:** Either:
- Drive these from real signals (e.g. engagement score from call engagement rate in `phiwe_call_timing_optimized.csv`, goal score from `phiwe_ramp_vs_target.csv` on-track booleans), or
- Remove them from the score entirely and calculate health from performance metrics only, with a clear note that engagement and goal alignment scoring requires additional data

Do not leave hardcoded placeholder values in a function that presents as dynamic scoring.

## Fix 3 — `benchmarks.py`: Label Mismatch

**File:** `benchmarks.py`

**Problem:** The module docstring and comments describe thresholds as "Wellness/Assisted Stretching Industry Standards" and "industry average." This campaign is working dormant/old leads — not fresh inbound wellness prospects. Using general industry benchmarks misstates the context and produces incorrect pass/fail assessments.

**Required fix:** Add a `benchmark_context` flag that the calling code can use to ensure the correct label is applied at the presentation layer:

```python
BENCHMARK_CONTEXT = {
    'label': 'Cold Re-Engagement Outreach Standard',
    'description': 'Benchmarks reflect cold outreach to dormant leads, not inbound or warm lead performance',
    'note': 'These thresholds are calibrated for SDR campaigns working old lead lists'
}
```

Additionally, review the current threshold values to confirm they are appropriate for cold re-engagement rather than general wellness industry. The key values to review:
- `show_rate['average']` — 15% may be high for cold outreach to dormant leads
- `cancel_rate['poor']` — 20% cutoff may be too lenient for this lead quality
- `engagement_rate` thresholds — 65–85% answer rate range appears calibrated for warm leads, not cold lists

Do not change values without confirming against actual cold re-engagement outreach data. The fix here is first to apply the correct label; threshold values are a second-order question.

## Fix 4 — `root_cause_analysis.json`: Zero-Count Causes Carry High-Impact Labels

**File:** Generated by the pipeline into `outputs/YYYY-MM-DD/root_cause_analysis.json`

**Problem:** The pipeline outputs root causes with `count: 0` and `impact: "High"`. Any downstream consumer (the dashboard app) that reads impact without checking count will surface these as findings. The "Long booking windows (>14 days)" cause is a known example — it was hypothesised as high-impact but has not appeared in the actual cancellation data.

**Required fix:** Update the script that generates `root_cause_analysis.json` to either:
- Filter out zero-count causes before writing to JSON, or
- Add an `active` boolean field: `"active": true` only when `count > 0`

The dashboard app should only render causes where `active: true` (or `count > 0` if the filter approach is used).

**Additional fix — action field language:** The `action` field for the low-touchpoint cause currently reads `"Require 3-call minimum before booking"`. This specific framing must never reach the client-facing layer — it creates a contractual reference point. When the dashboard renders this action, it must be rewritten as a confirmation follow-up protocol: describe what Phiwe does to protect hold rates, not a number the studio can audit against. The raw `action` field in the JSON can retain the internal logic value for pipeline use — the translation to client language is the UI layer's responsibility.

## Fix 5 — `validate_attribution.py`: Syntax Error in Pipeline Check

**File:** `validate_attribution.py` line 160

**Problem:** There is a malformed f-string in Check 5:
```python
print(f"- Future bookings in pipeline: {pipeline['bookings_count'].sum():.0f if not pipeline.empty else 0}")
```
This will raise a `ValueError` at runtime because the ternary expression is inside the format spec. Additionally, `pipeline` likely does not have a `bookings_count` column — the pipeline CSV uses individual row records, not aggregated counts.

**Required fix:**
```python
pipeline_count = len(pipeline) if not pipeline.empty else 0
print(f"- Future bookings in pipeline: {pipeline_count}")
```

## Fix 6 — `analytics.py`: ROI Uses Potential LTV as Default

**File:** `analytics.py` → `score_campaign_health()`

**Problem:**
```python
roi = revenue.get('roi_potential_average', revenue.get('roi_actual', 0))
```
The health score defaults to `roi_potential_average` — which is a projected LTV figure, not actual revenue. This means the score is being driven by aspirational LTV numbers, not what has actually been earned. The campaign could have near-zero actual ROI but score well because of LTV projections.

**Required fix:** Health scoring should use `roi_actual` as the primary signal. LTV projections are useful for context but should not drive the health score.

```python
roi = revenue.get('roi_actual', 0)
```

If the score always looks red on actual ROI alone and that is not useful, the fix is to redesign the scoring bands — not to use a projected number as the primary signal.

## Fix 7 — `analytics.py`: Forecast Show Rate Falls Back to 0.15

**File:** `analytics.py` → `forecast_30_days()`

**Problem:**
```python
recent_show_rate = last_7_days['shows'].sum() / last_7_days['new_bookings'].sum() if last_7_days['new_bookings'].sum() > 0 else 0.15
```
If there are no bookings in the last 7 days, the forecast defaults to a 15% show rate assumption. This is the industry average from `benchmarks.py` — but as noted in Fix 3, these benchmarks may not be calibrated for cold re-engagement. More importantly, a fallback of 0.15 with no data should be treated as insufficient data, not as a valid forecast input.

**Required fix:** If `last_7_days['new_bookings'].sum() == 0`, return the insufficient data response rather than proceeding with a fabricated show rate:
```python
if last_7_days['new_bookings'].sum() == 0:
    return pd.DataFrame({
        'scenario': ['insufficient_data'],
        'probability': [1.0],
        'bookings': [0],
        'shows': [0],
        'revenue_conservative': [0],
        'revenue_average': [0],
        'confidence': ['low'],
        'drivers': ['No bookings in last 7 days — insufficient data for forecast']
    })
```
